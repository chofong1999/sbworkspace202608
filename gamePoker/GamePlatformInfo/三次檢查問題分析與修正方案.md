### A7－A8. WebSocket 與輪詢並未真正互為備援

位置：

- `poker/server/PokerWebSocketHandler.java:23-44`
- `poker/service/impl/PokerGameServiceImpl.java:102-107`
- `poker/poker.js:175-205、611-628`
- `tjpoker/` 對應檔案

問題：

1. 前端 WebSocket 關閉後顯示「改用輪詢同步」，但後端 `afterConnectionClosed()` 立即呼叫 `leave()`，清除同一個 seat token；後續輪詢會得到 `INVALID_PLAYER`。
2. 正常按下離開時，前端先關 WebSocket 再送 DELETE。WebSocket close 與 DELETE 都會呼叫 `leave()`，形成雙重離場競態；第二個請求可能失敗，只是前端用 `complete` 導頁而看不到錯誤。
3. Handler 只在建立連線時送出字串 `connected`，沒有廣播房間狀態；真正同步仍是每 800 ms REST 輪詢。
4. seat token 放在 WebSocket query string，可能進入伺服器、反向代理或除錯日誌。

修正方案：

- 將「暫時斷線」與「玩家明確離場」拆成不同動作；WebSocket close 只標記連線狀態或保留短暫重連期限，不直接註銷 seat token。
- 只有明確 DELETE、房間結束或逾時清理才真正釋放 token。
- `leave()` 做成可重複呼叫的冪等操作，避免 close／DELETE 先後次序造成錯誤。
- 若維持輪詢，應把 WebSocket 定位為連線提示而非同步備援；若要真正使用 WebSocket，需建立房間 session 註冊與狀態變更廣播。
- 此項修正後，原清單第 6 項才可重新標示完成。

### A9. 正式 Poker 直接入口無法完成加入

位置：

- `management/config/GameDataInitializer.java:22-32`
- `poker/controller/PokerGameController.java:42-50`
- `poker/poker.js:29-53、140-162`

問題：

Game Management 的 frontend path 直接指向 `poker_client.html`，頁面仍顯示電腦／玩家加入按鈕。非平台模式按下按鈕時只送 `roomId`，但正式 Controller 一律要求 JWT、`modeId`、Lobby Room 及 account 成員核對，所以這組直接加入 UI 與後端契約不相容。

修正方案：

- 依「所有模式都先建立平台房間」的既定設計，正式 Poker 頁面只接受 Lobby／Board 帶入的 room 參數；缺少房間時顯示返回大廳，不顯示無法使用的獨立加入按鈕。
- 若仍要保留獨立測試入口，應只留在 Tjpoker 或專用測試 profile，不讓正式 POKER 共用兩套加入契約。

### A10. 兩份房間生命週期尚未接合

位置：

- `poker/model/GameRoom.java`
- `poker/service/impl/PokerGameServiceImpl.java:102-107、259-281`
- Lobby 端位置列在其他組員 B1。

問題：

Poker `FINISHED` 只更新記憶體 GameRoom；`leave()` 只改 Poker 連線資料。Lobby Room 沒有同步結束或刪除，Poker `rooms` map 也沒有移除時機，因此一房一局的程式端閉環仍未完成。

修正方案：

- 先由 Poker／Lobby 約定唯一生命週期契約：正常結束、單方中離、房主中離、雙方離場各由誰把 Lobby Room 改為結束並刪除。
- Poker 端在契約完成後加入 GameRoom 清理入口；不要在尚未確認 Lobby 狀態時自行刪除另一組資料。

### A11. 所有 Poker 房間共用同一把鎖

位置：

- `poker/service/impl/PokerGameServiceImpl.java:34、39、102、110、145、178、190、202、212`
- `tjpoker/service/impl/TjpokerGameServiceImpl.java` 對應方法

問題：

Service 是 singleton，所有公開方法都宣告 `synchronized`。不同 roomId 也會互相等待；其中 `autoSelect` 會進行大量牌組計算，而每位玩家又固定輪詢，房間數增加後會互相拖慢。

修正方案：

- rooms 容器與單一房間狀態分開保護；只鎖目前操作的 GameRoom，不要鎖整個 Service。
- 若要改用 `ConcurrentHashMap` 或房間級 lock，先依課程技術限制向使用者說明；本課程規模也可先用簡單的「取得 room 後 `synchronized(room)`」設計。

### A12. 初始化器只新增、不更新

位置：

- `management/config/GameDataInitializer.java:22-67、70-88`

問題：

Game／GameMode 只在找不到時建立；既有資料的 path、enabled、玩家數及名稱完全不會依新版程式調整。程式碼改過後，舊 DB 仍可能保留舊設定，因而讓「刪 DB」看似是唯一修復方式。

修正方案：

- 先明確決定資料性質：若是可由管理員修改的業務資料，initializer 只負責第一次 seed，之後變更應使用 migration 或管理 API；若是固定系統資料，initializer 應依 gameCode／modeCode 更新需要強制一致的欄位。
- 不應同時把資料當成可編輯設定，又期待每次啟動自動覆蓋。

### A13. GameMode 唯一性只有 Service 檢查

位置：

- `management/model/GameMode.java:10-36`
- `management/service/impl/GameManagementServiceImpl.java:168-189`
- `management/repository/GameModeRepository.java:10-14`

問題：

Service 先查詢再新增，但資料表只有主鍵 index，沒有 `(game_id, mode_code)` unique constraint。兩個同時新增的請求可能都通過查詢並寫入重複 modeCode，之後回傳 `Optional` 的 repository 查詢也可能因多筆結果失敗。

修正方案：

- 在資料庫層加入 gameId＋modeCode 複合唯一約束，Service 的友善錯誤檢查保留。
- 既有 DB 加約束前先檢查並整理重複資料。

### A14. 刪除 Game／Mode 會留下跨模組孤兒資料

位置：

- `management/service/impl/GameManagementServiceImpl.java:80-111`
- `management/model/GameMode.java:17-21`
- `lobby/entity/Room.java:20-24`
- `board/entity/TeamPost.java:23-32`

問題：

刪除 Game 時會刪自己的 modes，刪除 mode 也沒有使用中檢查；Lobby Room 與 Board TeamPost 只保存數字 ID，SQLite schema 沒有對 games／game_modes 的外鍵。若管理員刪除已被使用的資料，舊房間與公告會留下無法解析的 ID。

修正方案：

- 優先以 `enabled=false` 取代實體刪除已使用的 Game／Mode。
- 若仍提供 DELETE，先建立跨模組「是否被 Room／TeamPost 使用」檢查；資料庫外鍵與刪除策略須由各模組共同決定，不能只改 management 單邊。

### A15. Tjpoker 仍是另一套較弱契約

位置：

- `tjpoker/service/impl/TjpokerGameServiceImpl.java:38-80`
- `tjpoker/server/TjpokerWebSocketHandler.java`
- `tjpoker/poker.js`

問題：

Tjpoker token 由 roomId、時間與 `Math.random()` 組成，沒有 User／account 身分，也沒有正式 Lobby 核對；正式 Poker 則使用 UUID、JWT 與 Lobby account。Chat 目前仍載入 Tjpoker，因此停用測試版並非完全沒有使用者。

修正方案：

- 先決定 Tjpoker 是純本機測試工具、要與正式 Poker 合併，或要移除。
- 若保留可連線測試，至少將 token 改為不可預測的 UUID，並明確限制它不能當正式平台入口。

### A16. 舊核心殘留跨房間狀態與兩套洗牌

位置：

- `poker/model/Game.java:6-18、56-66、338-363`
- `poker/service/impl/PokerRuleServiceImpl.java:17-53`
- `tjpoker/` 對應檔案

問題：

`counter`、`game_index`、`rounds_tmp`、`stage` 是 static，所有 GameRoom 共用；目前新 Service 大多沒有使用這些欄位，但每次建立 Game 仍會改寫部分 static 值，屬於容易造成未來跨房間污染的舊狀態。

另外實際發牌使用 `Game.shuffle_02()`，PokerRuleServiceImpl 另有一套目前未使用的 `resetPlayers()`／shuffle；後者每一輪都從整副牌任意交換，不是標準 Fisher–Yates。兩套新局入口的行為不一致。

修正方案：

- 先以搜尋與測試證明 static 流程確實沒有外部使用，再依 RULE-0008 討論改成 instance state 或移除；不能未經討論重寫舊核心。
- 決定唯一的新局／洗牌入口。若保留 RuleService 的洗牌，改成與正式 Game 相同的均勻策略並補分布與不重複測試。

### A17. 測試仍缺少重要整合情境

位置：

- `backend/src/test/java/com/example/demo/modules/game/poker/`
- `backend/src/test/java/com/example/demo/modules/game/tjpoker/`

目前直接 Service／Controller 測試可通過，但沒有覆蓋：

- WebSocket 意外斷線後 REST 輪詢是否仍有效。
- WebSocket close 與 REST DELETE 同時發生。
- 兩個不同 roomId 是否互相阻塞或污染。
- 正式頁面無 room 參數時的行為。
- 兩個實際瀏覽器完整三輪、返回 Lobby 與 Chat iframe 點擊。
- `Round` 花色比較使用字串參考比較 `!=` 的邊界情況。

修正方案是先補 WebSocket／離場 Service 測試，再做雙瀏覽器手動流程；規則核心另補同點數不同花色、順子、同花與平手不應發生等邊界測試。

### B1－B2. Lobby 房間生命週期與輸入契約

共同位置：`backend/src/main/java/com/example/demo/modules/lobby/`

位置：

- `entity/Room.java:20-48`
- `controller/LobbyController.java:89-168、245-349、388-439`
- `server/RoomWebSocketHandler.java:20-38`

問題：

- `/status` 固定回傳沒有進行中遊戲。
- 建房、加入、離開、踢人、設定及開始使用 request 內的 account，沒有由 JWT 決定操作者。
- playerCount／modeId／maxPlayers 可由前端傳入，部分流程沒有完整核對 GameMode 所屬遊戲、enabled 與人數範圍。
- Lobby 開始後改為 PLAYING，但 Poker FINISHED／leave 沒有回寫或刪除 Lobby Room。
- WebSocket query 解析脆弱，關閉後沒有清除 session map。

修正方案：

- Lobby 操作者由 JWT account 取得，request 只帶目標資料。
- GameMode 一律經 game/management Service 查詢；房間保存建立當下快照，但不得由 request 任意覆蓋。
- 與 Poker 訂出結束、離場、刪房及錯誤重試契約，並指定單一負責方。
- WebSocket 使用可靠 query parser，連線與關線都維護 session map。

### B3. Board 與 Poker 使用不同 ID 命名空間

共同位置：`backend/src/main/java/com/example/demo/modules/board/`

位置：

- `entity/Member.java:17-21`
- `service/BoardSessionService.java:31`
- `service/BoardTeamService.java:89-100`
- Poker 端：`game/poker/service/impl/PokerGameServiceImpl.java:39-65`

問題：

Board Member 已保存 `platformUserId`，但 `joinGame()` 呼叫 Poker 時傳入 `member.getId()`。正常 Lobby Poker 則從 JWT 傳平台 `UserResponse.id()`。同一個 Poker `userId` 欄位因此可能混用兩個不同資料表的 ID；同一真人經不同入口可能被當成兩位玩家，數字碰巧相同時也可能把不同人視為同一人。

修正方案：

- Poker 的玩家身分明確統一為 platform User ID；Board 應先確認 Member 已綁定 platformUserId，再傳該值。
- 房間成員資格仍用 account 與 Lobby 名單核對；userId 用於 Poker 重連／座位識別，兩者職責不要混用。

### B4. Board 權限依賴可偽造的 ID

位置：

- `controller/BoardTeamController.java:17-34`
- `controller/InteractionController.java:20-69`
- `service/TeamPostService.java:49-80`
- `service/InteractionService.java:53-112`

問題：

Service 雖檢查 captainId 是否等於公告隊長，但 captainId／memberId 由 path、query 或 body 提供；全域 API 又是 permitAll。呼叫者只要填真正隊長 ID 就可能通過。刪除 TeamPost 與 Comment 更沒有作者／隊長檢查。

修正方案：

- Controller 從 JWT／Board session 取得 platformUserId，再解析對應 Member；不可使用 request ID 當登入身分。
- update、delete、review、kick、start、favorite、通知查詢及留言刪除都以登入者身分做所有權或角色判斷。

問題：

- 主 iframe 預設載入停用的 Tjpoker，不是正式 Poker。
- 主頁的 send 只寫本機 DOM，WebSocket send 被註解；真正 WebSocket client.js 未載入。
- 另有固定 admin／1234 登入與兩套 `/ws/chat` server 流程。

修正方案：

- 聊天關閉時讓整個外層 overlay `pointer-events:none`，只在展開面板與按鈕恢復事件。
- 主內容入口交給 Lobby／Game Management，不固定寫 Tjpoker。
- 保留一套 Chat WebSocket server 與一套實際載入的 client，移除固定測試登入。

### B6. Quiz 正解、計分、時間與排行榜身分

共同後端位置：`backend/src/main/java/com/example/demo/modules/game/quiz/`

共同前端位置：`frontend/src/pages/Games/quiz/`

位置：

- `controller/QuestionsController.java:35-73`

- `dto/QuizSubmitRequest.java:12-28`
- `service/QuizService.java:132-210`
- `service/PlayerService.java:23-35`

問題：

- `/exam` 直接回傳 `Option.isCorrect`。
- 題庫新增、修改、刪除公開；富文字直接保存並插入 `innerHTML`。
- 分數分母是 request 的 `answers.size()`；只提交一題正確答案或重複同一題可得到 100 分。
- 沒有 server-side exam session，不能確認題目集合，也沒有伺服器計時；倒數完全在前端。
- 排行榜 username 由 request body 指定，未綁定 JWT，可以替其他名稱提交高分。

修正方案：

- 開始測驗時由後端建立 exam attempt，保存題目 ID、開始／到期時間與登入 userId；提交只接受該 attempt 的答案。

### B7－B8. User 初始化與 Board 測試契約

共同位置：`backend/src/main/java/com/example/demo/modules/user/`

測試位置：`backend/src/test/java/com/example/demo/modules/board/BoardSessionIntegrationTests.java`

位置：

- `database/UserDatabaseInitializer.java:76-101`
- `service/UserService.java:226-250`
- `security/SecurityConfig.java:37-49`
- `BoardSessionIntegrationTests.java:46、63、83、110`

問題：

- 每次啟動直接 INSERT admin，第二次啟動會觸發 users.account unique constraint；刪 DB 只能讓下一次成功，不能根治。
- 2026-09-03 的實際啟動日誌再次確認：`BeanCreationException` 發生在 `UserDatabaseInitializer.insertDefaultAdmin()` 第 84 行，根因為 `SQLITE_CONSTRAINT_UNIQUE: users.account`；此錯誤與 `GameMode.modeId` 無關。
- UserService 只允許英數帳密，但 Board 測試用 UUID 與密碼包含 `-`，五項測試在建立 User 前就失敗。
- Security matcher 與實際 Board auth 路徑不一致，後續 `/**.permitAll()` 讓其他 API 都公開。

修正方案：

- 初始化 admin 前依 account 查詢；不存在才建立，或使用可重複執行的 migration／upsert。
- Board 測試資料遵守正式 User 規則；若產品需求確實允許連字號，則由 User 組先修改正式規格與驗證，再調整測試，不能只為通過測試放寬。
- 依模組列出公開、登入及 ADMIN endpoint，移除涵蓋全部路徑的臨時 permitAll。

### B9. CORS、WebSocket origin 與 JWT secret

位置：

- `user/security/SecurityConfig.java`
- `board/config/CorsConfig.java`
- 各模組 Controller 的 `@CrossOrigin`
- 各模組 `server/*WebSocketConfig.java`
- `backend/src/main/resources/application.properties:15-16`

問題：REST 與 WebSocket 各自允許不同範圍，許多位置使用 `*`；JWT secret 固定提交在 repository。正式 HTTPS、credentials 與不同 port 部署時會不一致。

修正方案：由共用設定提供單一允許來源清單，REST 與 WebSocket 使用同一環境設定；JWT secret 從環境變數或未提交的本機設定取得。
