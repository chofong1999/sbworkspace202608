# 使用者制度與功能說明

> 給任何採用這套制度的使用者；AI正常接手不必閱讀。

## 最簡單的用法

- 第一次建立資料：`！首次交接`，或直接說要交接。
- 下一個AI開始：`！接手`。
- 真的要暫停、換對話或換AI時：`！交接`。
- 只想看資料：`！只查看`。

同一對話連續工作時，不需要每做完一件小事就交接。AI完成一次回覆、工具執行或小成果後，仍由原工作者保有工作權並繼續；只有明確結束這段工作時才交接。

指令第一個非空白字元使用全形`！`或半形`!`。沒有符號也可以照平常方式說話，AI會依意思判斷；句尾的驚嘆號不算明確指令。

## 功能

| 功能 | 明確指令 | 何時使用 |
|---|---|---|
| 首次交接 | `！首次交接` | 建立尚未初始化的交接資料 |
| 接手工作 | `！接手` | 狀態為可接續，由新對話或另一名員工開始 |
| 完成交接 | `！交接` | 暫停、結束、換對話／AI或要釋放工作權 |
| 只查看 | `！只查看` | 不想登記或改狀態 |
| 檢查狀態 | `！檢查狀態` | 只想知道目前能否接手 |
| 查看規則 | `！查看規則 [篩選]` | 查看AI目前採用的規則、強度、範圍與理解 |
| 修改規則 | `！修改規則 RULE-ID 修改內容` | 直接更正特定規則，避免使用者與AI長期理解不同 |
| 能力檢查 | `！能力檢查 [任務]` | 執行前確認資料、工具、權限與驗證能力是否足夠 |
| 處理建議 | `！處理建議` | 失敗或異常時查看原因、替代方案、成本與模型建議 |
| 升級版本 | `！升級版本` | 已提供新版樣板與現有資料 |
| 更新知識庫 | `！更新知識庫` | 已提供知識套件 |
| 封存日誌 | `！封存日誌` | 明確要整理舊日誌 |
| AI使用回饋 | `！填問卷` | 請實際使用過本制度的AI填回饋 |
| 問題回報 | `！問題回報` | 記錄可重現問題、制度缺陷或可重用解方 |

指令條件不符時，AI不會硬做或猜成別的功能，只會說明主要不符條件與下一步。功能已完成時也不會重複執行。

## 工作階段、檢查點與世代

- **模型回合：** 一次AI回覆或工具執行。
- **單項成果：** 一張圖、一段程式或一節筆記等小成果。
- **工作階段：** 同一AI對話持有工作權並持續工作，可包含很多回合與成果。
- **正式交接：** 工作階段結束，釋放工作權並留下可供下一名員工接續的快照。
- **交接世代：** 成功形成正式快照的次數，不是AI回覆數或成果數。

回覆結束、小成果完成、使用者追問、補充或要求修正，都不會自行增加世代。同一工作階段的多項差異在最後合併成一筆日誌與一個世代。

長工作在重要里程碑或中斷後很難重建時，AI可把最小現況寫進`12_當前工作.md`的「工作中檢查點」。它不釋放工作權、不寫新日誌、不增加世代，也不代表成果已正式交接。

如果AI對話意外中斷而狀態仍是`工作中`，新AI不能只因時間經過就奪取工作權；應先依異常流程核對工作者、檢查點與實際成果。

## 規則透明化

每條長期規則在`11_本工作規則.md`有穩定的`RULE-ID`，強度只分為：

- `必須`：不能自行偏離。
- `禁止`：不能執行。
- `一般`：預設遵守，可依情況合理調整。
- `偏好`：期望方向，使用極低／低／高／極高表示採用頻率。

`！查看規則`可用`全部／強制／一般／偏好／RULE-ID／關鍵字`篩選。輸出直接來自`11`，不保存第二份容易過期的清單。

`！修改規則`會先重述舊規則、新規則及影響範圍；若你的說法可能有兩種實質不同解讀，AI會先問一次。規則內容改寫時ID保持不變，刪除後也不重用舊ID。

## 能力檢查、執行契約與完成狀態

AI不能只因「已經做了」或「看起來正常」就宣稱完成。執行前會依風險調整檢查：

- 低風險讀取或單檔工作維持原有最低檢查，不增加大量流程。
- 多檔、批次、外部資料、工具依賴、曾失敗或高風險工作，才做完整能力預檢並讀取適用契約。

高風險強制規則可引用按需「執行契約」，明確規定必要輸入、權威來源、缺少時怎麼辦、驗證方法與通過證據。簡單工作不必讀全部契約。

當前成果狀態只使用：`已完成`、`已產出未驗證`、`部分完成`、`驗證未通過`、`受阻`、`無法可靠完成`。只有所有適用的強制規則與契約都通過、明確不適用，或經你明示授權降級後，才能使用`已完成`。

`！能力檢查`本身只診斷，不預先接手或修改檔案；無法確認的能力會寫`未知`，不把AI自述當證據。

## 失敗與處理建議

相同方法第二次失敗、規則讀到卻漏做、完成宣告與成果矛盾，或缺少必要資料／權限時，AI應停止機械重試並分類原因。

`！處理建議`會列出：失敗項、仍可靠的成果、可能原因與信心、最多三項排序後的處理方式、各自成本與可能失去的保障。

換較強模型只在問題確實來自推理、長文規則遵循或複雜工具協調時有幫助。缺少檔案、權限、平台功能或你的決定時，換模型無法解決；AI必須明說。

## 平常只需看兩個地方

1. `使用者_目前狀態與待辦.md`：最近正式交接快照、你現在要做什麼。
2. `回饋與問題_待交付`：要交給制度維護者的AI回饋與問題報告；沒有檔案時不用理會。

工作進行中的即時工作者與狀態需要時才看`00_先讀_身分與啟動.md`；詳細下一步與未驗證狀態看`12_當前工作.md`。

## 使用原則

- 每份工作使用一個交接資料夾；同一時間只讓一名AI修改正式工作。
- 一個AI對話是一名員工；同帳號的新對話仍是新員工。
- 只查看、查看規則、能力檢查與處理建議不接手、不登記、不改狀態。
- 新AI通常讀長期背景、規則與當前工作；舊AI依未讀量選擇零差異、增量或快照重新入職。
- 正常接手不重算完整雜湊、不重跑完整QA，也不讀全部歷史或全部契約。
- 這套制度不是成果備份或Git。

## 回饋與問題

`！填問卷`會讓AI依自己的直接使用經驗複製空白表單，填好後放入`回饋與問題_待交付`，並告訴你完整位置；平台支援附件時也應提供檔案。沒有直接使用經驗時不得編造。

`！問題回報`會建立一份具體問題報告。實際工作中遇到高價值、可能重複的制度問題時，目前工作者也可自動記錄；只查看模式不會偷偷寫入。

空白原件永遠留在`80_按需/60_回饋與問題`，填寫時另建檔案，不得覆蓋。另附選用的`使用者回饋表單.html`；按「提交並保存」後，支援的瀏覽器會要求你選擇一次交接資料夾或輸出資料夾，並直接建立Markdown。不支援時才退回一般下載。

## 升級版本

提供新版樣板與目前交接資料後使用`！升級版本`即可。AI會自行分辨同制度升級、不同制度轉入或空白首次交接。

1.12升級會為所有仍有效長期規則建立RULE-ID，只為符合門檻的高風險規則建立契約，並把成果狀態轉成標準狀態。既有歷史與世代保持原文，不因舊版曾頻繁交接而竄改。

升級只檢查manifest列出的現役制度檔與本輪相依工作欄位。歷史、封存、知識庫內容及回饋輸出不當成升級殘留；填好的回饋原樣保留。

## 與其他工作系統協作

作圖、測試或其他子系統可在第一次正式寫入前自動取得工作權。交接資料只保存其最短里程碑摘要及詳細入口，不複製領域規則、逐項QA或完整歷史。一次子系統操作完成不代表工作階段結束。

## 知識庫與異常

知識庫獨立更新，不必為新增解法升級制度。AI只在遇到具體錯誤時定向查索引，不會正常接手就讀完整知識庫。

低風險問題自行處理；深入檢查成本高而效益不確定時提供選項；需要權限、可能破壞資料或正式來源衝突時才要求使用者處理。只有使用者摘要顯示`需要使用者處理`時才必須介入。
